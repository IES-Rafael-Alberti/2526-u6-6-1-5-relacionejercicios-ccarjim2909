### S — SRP (Single Responsibility Principle)

**Código v0:** `es.ies.ejercicios.u6.ej65.srp`

Tarea:

- Identifica una clase/función que hace “demasiadas cosas”.
- Separa responsabilidades en tipos más pequeños (por ejemplo: normalización, formateo, persistencia, logging).
- Mantén un `main`/demo que pruebe el flujo.

Pista:

- Si una clase cambia por más de un motivo (cambiar el formato del informe, cambiar la regla de normalización, cambiar el logging, cambiar cómo se obtienen los datos), probablemente está violando SRP.
- En v0 fíjate en: preparación de datos + registro/normalización + generación de informe + salida por consola, todo junto. Intenta extraer al menos 2 componentes con nombres claros.

Preguntas:

1) ¿Qué responsabilidades tenía la versión v0?  

RESPUESTA:

La clase `InformeAppServiceV0` tenía varias responsabilidades mezcladas en un solo método:

-   Preparar los datos del programa (crear la lista de personas y alumnos).

-   Registrar personas utilizando `RegistroPersonas`.

-   Generar un informe en formato Markdown.

-   Mostrar mensajes y resultados por consola.

Esto viola el principio **SRP**, ya que la clase podría cambiar por varios motivos distintos (cambio en datos, en registro, en generación de informes o en el logging).

2) ¿Qué clases/componentes has creado y qué responsabilidad tiene cada uno?

RESPUESTA:

Para cumplir SRP se separaron las responsabilidades en varios componentes:

-   **PreparadorDatos**: se encarga únicamente de crear la lista de elementos `Resumible`.

-   **ServicioRegistro**: gestiona el registro y búsqueda de personas.

-   **ServicioInforme**: genera el informe en formato Markdown.

-   **InformeAppService**: actúa como orquestador del flujo del programa.

De esta forma cada clase tiene una responsabilidad clara y definida.

3) ¿Cómo mejora el mantenimiento/testeo con el refactor?

RESPUESTA:

El refactor mejora el mantenimiento porque cada clase tiene una única responsabilidad, lo que facilita modificar una parte del sistema sin afectar a las demás.

También mejora el testeo porque cada componente puede probarse de forma independiente. Por ejemplo, se puede probar `ServicioInforme` sin necesidad de preparar datos ni registrar personas.


### O — OCP (Open/Closed Principle)

**Código v0:** `es.ies.ejercicios.u6.ej65.ocp`

Tarea:

- El generador v0 usa un `when` por “formato”.
- Refactoriza para que añadir un nuevo formato (p. ej. “HTML” o “JSON”) no requiera modificar el generador central.

Pista:

- Es normal que siga existiendo un punto donde “decides qué implementación crear” (CSV/Markdown/etc.).
- La idea de OCP es que esa decisión no obligue a modificar la **lógica principal** (el generador), sino que se haga fuera (por ejemplo en `main`, una factoría/registry o inyección de dependencias).

Preguntas:

1) ¿Qué parte violaba OCP y por qué?  

RESPUESTA:

La clase `GeneradorInformeV0` violaba el principio OCP porque utilizaba un `when` basado en el enum `FormatoInformeV0` para decidir cómo generar el informe.

Cada vez que se quería añadir un nuevo formato (por ejemplo HTML o JSON), era necesario modificar el enum y añadir una nueva rama al `when`, lo que obligaba a modificar el código existente.

Esto rompe OCP porque el código no está cerrado a modificación.


2) ¿Qué técnica has usado (polimorfismo/estrategia/jerarquía) para cumplir OCP?

RESPUESTA:

Se ha utilizado **polimorfismo mediante una interfaz (`GeneradorInforme`)**.

Cada formato de informe se implementa como una clase distinta (`GeneradorCsv`, `GeneradorMarkdown`, etc.) que implementa esta interfaz.

De esta forma el código puede extenderse añadiendo nuevas clases sin modificar las existentes.


3) ¿Cómo añadirías un nuevo formato tras tu refactor?

RESPUESTA:

Para añadir un nuevo formato solo sería necesario crear una nueva clase que implemente la interfaz `GeneradorInforme`.

Por ejemplo, para crear un informe en HTML se puede crear una clase `GeneradorHtml` que implemente el método `generar`.

Después se puede utilizar directamente desde `main` u otro componente sin modificar el generador existente.


### L — LSP (Liskov Substitution Principle)

**Código v0:** `es.ies.ejercicios.u6.ej65.lsp`

Tarea:

- Hay una jerarquía donde una subclase rompe expectativas del tipo padre (comportamiento inesperado).
- Refactoriza para que cualquier subclase pueda sustituir al padre sin “sorpresas” (sin lanzar excepciones inesperadas, sin romper invariantes).

Pista:

- Si una “subclase” no puede cumplir el contrato del padre (por ejemplo, “solo lectura” no puede `guardar`), normalmente no debe heredar de ese tipo.
- Una solución habitual es separar interfaces por capacidades (lectura vs escritura) o usar composición para exponer solo lo que realmente se puede hacer.

Preguntas:

1) ¿Qué comportamiento concreto violaba LSP?  

RESPUESTA:

La clase `RepositorioSoloLecturaV0` heredaba de `RepositorioPersonasV0`, pero sobrescribía el método `guardar()` lanzando una excepción `UnsupportedOperationException`.

El código cliente esperaba que cualquier `RepositorioPersonasV0` permitiera guardar personas, pero al sustituirlo por `RepositorioSoloLecturaV0` el programa fallaba en tiempo de ejecución.

Esto rompe el principio LSP porque la subclase no cumple el contrato del tipo padre.

2) ¿Qué cambio has hecho para asegurar sustitución válida?

RESPUESTA:

Se separaron las capacidades del repositorio en dos interfaces:

-   `RepositorioLectura` → permite buscar personas.

-   `RepositorioEscritura` → permite guardar personas.

El repositorio completo implementa ambas interfaces, mientras que el repositorio de solo lectura implementa únicamente `RepositorioLectura`.

De esta forma ningún tipo se ve obligado a implementar operaciones que no puede cumplir.

3) ¿Cómo lo demostrarías con una prueba/ejemplo?

RESPUESTA:

En el código refactorizado el cliente depende únicamente de la interfaz `RepositorioLectura`.

Esto permite utilizar tanto un repositorio completo como uno de solo lectura sin que el programa falle.

Por ejemplo:

    cliente(RepositorioPersonas())

    cliente(RepositorioSoloLectura(...))

Ambos funcionan correctamente sin lanzar excepciones.


### I — ISP (Interface Segregation Principle)

**Código v0:** `es.ies.ejercicios.u6.ej65.isp`

Tarea:

- La interfaz v0 es “gorda” (métodos no usados por algunos clientes).
- Divídela en interfaces pequeñas y adapta los clientes para depender solo de lo que usan.

Pista:

- Empieza por el cliente más pequeño: si un cliente solo necesita `buscar(...)`, no debería depender de `exportarCsv()` ni `borrarTodo()`.
- Segrega por capacidades (por ejemplo: lectura, escritura, exportación, borrado) y haz que cada cliente dependa solo de lo que usa.
- Señal típica de violación: ganas de dejar métodos vacíos, lanzar `UnsupportedOperationException` o meter `TODO(...)` al implementar.

Nota (relación con LSP):

- ISP y LSP suelen aparecer juntas: una interfaz “gorda” puede forzar a ciertos tipos a prometer operaciones que realmente no pueden cumplir, lo que termina rompiendo la sustitución (LSP).
- Segregar por capacidades (por ejemplo, lectura vs escritura) ayuda a que los tipos implementen solo contratos que pueden respetar, mejorando el cumplimiento de LSP.

Preguntas:

1) ¿Qué métodos eran irrelevantes para algún cliente?  

RESPUESTA:

En la interfaz `RepositorioPersonasCompletoV0` existían varios métodos que no eran necesarios para todos los clientes.

Por ejemplo, la clase `BuscadorPersonasV0` solo necesitaba utilizar el método `buscar()`, pero estaba obligada a depender también de `guardar()`, `exportarCsv()` y `borrarTodo()`.

Esto viola el principio ISP porque el cliente depende de métodos que no utiliza.


2) ¿Cómo has segregado la interfaz (nombres y responsabilidades)?

RESPUESTA:

La interfaz original se dividió en varias interfaces más pequeñas, cada una con una responsabilidad concreta:

-   `RepositorioLectura` → buscar personas.

-   `RepositorioEscritura` → guardar personas.

-   `RepositorioExportador` → exportar datos en CSV.

-   `RepositorioMantenimiento` → borrar todos los registros.

De esta forma cada cliente depende únicamente de la interfaz que realmente necesita.


3) ¿Qué mejora aporta a largo plazo?

RESPUESTA:

La segregación de interfaces mejora el diseño del sistema porque reduce el acoplamiento entre componentes.

Además facilita el mantenimiento y la evolución del código, ya que nuevos clientes pueden depender solo de las capacidades que necesiten sin verse obligados a implementar o conocer métodos innecesarios. 


### D — DIP (Dependency Inversion Principle)

**Código v0:** `es.ies.ejercicios.u6.ej65.dip`

Tarea:

- Un módulo de alto nivel depende directamente de una implementación concreta.
- Refactoriza para que dependa de **abstracciones** e inyecte implementaciones (constructor recomendado).

Pista:

- “Alto nivel” = orquesta el caso de uso; “bajo nivel” = detalles concretos (CSV/Markdown, consola/archivo, etc.).
- Crea una abstracción (interfaz) que represente lo que necesitas (p. ej. `GeneradorInforme`), y pasa la implementación por **constructor**.
- Si para cambiar de CSV a Markdown tienes que editar la clase de alto nivel, aún no estás cumpliendo DIP.

Preguntas:

1) ¿Cuál era el detalle concreto del que dependía el módulo de alto nivel?  

RESPUESTA:

El módulo de alto nivel `ControladorInformesV0` dependía directamente de la clase concreta `InformeCsv`.\
Esto se ve en la línea donde se crea el objeto:

    private val generador = InformeCsv()

De esta forma, el controlador queda acoplado a una implementación específica de generación de informes en formato CSV.\
Si se quisiera cambiar el formato del informe (por ejemplo a Markdown u otro), habría que modificar el propio controlador, lo que viola el principio DIP.

2) ¿Qué abstracción has creado/empleado?

RESPUESTA:

Se ha creado la interfaz `GeneradorInforme`, que define el comportamiento necesario para generar informes sin depender de una implementación concreta.

Por ejemplo:

    interface GeneradorInforme {\
    fun generar(titulo: String, items: List<Resumible>): String\
    }

De esta forma, el módulo de alto nivel depende de una **abstracción** en lugar de depender directamente de una clase concreta como `InformeCsv`.

3) ¿Cómo intercambiarías implementaciones sin tocar el módulo de alto nivel?

RESPUESTA:

Las implementaciones se intercambian mediante **inyección de dependencias por constructor**.\
El controlador recibe un objeto que implementa la interfaz `GeneradorInforme` en su constructor:

    class ControladorInformes(private val generador: GeneradorInforme)

De esta manera, se puede pasar cualquier implementación (por ejemplo `GeneradorInformeCsv` o `GeneradorInformeMarkdown`) al crear el controlador:

    val controller = ControladorInformes(GeneradorInformeCsv())

Si se quisiera cambiar el formato del informe, solo habría que crear otra implementación de `GeneradorInforme` y pasarla al constructor, sin modificar la clase `ControladorInformes`.
